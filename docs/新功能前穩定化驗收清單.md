## 一、目前站在哪裡

目前產品已經不只是單一風險報告，流程已延伸為：

1. 整理租屋刊登資料。
2. 產生 RHIR 與 RRI 風險結果。
3. 用已審核案例補充風險依據。
4. 保存 AI 分析與個人策略。
5. 記錄刊登、看房、談判、簽約、點交與入住後事件。
6. 保存契約原檔，進行文字擷取與人工確認。

因此，現階段的重點不是再增加入口，而是確保同一間房、同一個時間點、同一份契約得到的資料不會互相混用。

## 三、優先級定義

| 等級 | 意思 | 開發規則 |
| --- | --- | --- |
| P0 | 可能造成資料被他人修改、原文遺失、錯用舊資料或核心流程不可用 | 未通過前，不加入新功能 |

## 四、完整驗收關卡

### 關卡 0：固定乾淨的開發起點（P0）

目的：避免把舊分支或展示素材誤當成新功能的一部分。

要完成：

- 新修正一律從最新 `main` 開始。
- 12 個未追蹤素材要決定「納入、移到專用資料夾、或忽略」，但不能在不明情況下批次提交。
- 舊 Claude 分支只做唯讀盤點，不直接合併。
- 每次只提交本次穩定化相關檔案。

通過標準：

- `git status --short --branch` 顯示分支正確。
- 本次提交內容沒有夾帶既有素材。
- 推送後本機與 GitHub 的提交相同。

### 關卡 1：封住案例審核權限（P0）

目的：避免公開訪客把案例改成「通過」、修改分類或審核備註。

目前問題：

- 案例可公開閱讀是產品需要。
- 案例的審核更新目前也允許匿名訪客操作，只適合內部原型。

要完成：

- 公開訪客只能讀取已允許公開的案例。
- 只有已登入、具有審核身分的人可以修改審核狀態與對應欄位。
- 未登入、一般登入者、審核者三種身分要有清楚不同結果。
- 審核操作要留下時間與操作者，且不能改寫官方原文。

通過標準：

- 未登入修改被拒絕。
- 一般登入者修改被拒絕。
- 審核者可以修改允許的欄位。
- 審核者不能改寫官方原始內容。
- 讀取案例仍能正常運作。

### 關卡 2：分清楚「程式壞掉」與「線上服務失聯」（P0）

目的：讓任何人看到檢查結果時，知道應該修程式、檢查設定，還是等待服務恢復。

要完成：

- 本機、不連網的檢查要能單獨全部執行。
- 需要 Supabase 的檢查要獨立執行。
- 線上檢查失敗時，要說明是網址無法解析、權限拒絕、資料表缺少，或內容不符合規則。
- README 要寫清楚線上檢查需要哪些前置條件，但不能放入私人密碼。

通過標準：

- 離線檢查全數通過。
- 線上服務正常時，案例對應與案例查詢皆通過。
- 線上服務中斷時，檢查能給出可辨識的原因，而不是只有 `fetch failed`。

### 關卡 3：確認資料庫版本與程式期待一致（P0）

目的：避免本機文件寫了新欄位，但線上資料庫仍停在舊版本。

要完成：

- 列出線上應存在的資料表、欄位與權限。
- 確認案例、AI 分析、個人策略、原始文件與文字擷取資料都已套用正確版本。
- 建立只讀檢查，指出缺少哪一張表或哪一個欄位。
- SQL 更新必須有固定順序，不能靠記憶手動猜測。

通過標準：

- 全新資料庫可依文件順序完成設定。
- 現有資料庫執行只讀檢查時沒有缺表或缺欄位。
- 重複執行安全的更新腳本不會破壞既有資料。

### 關卡 4：鎖定 XYZ 快照與策略依據（P0）

目的：避免使用者在看房或談判後更新資料，畫面卻仍顯示舊分析，或新策略引用舊契約。

要完成：

- 每次 AI 分析記住自己依據的案件、版本、事件與快照。
- 每次個人策略記住相同依據。
- 新事件改變風險資料後，舊分析與舊策略要明確標示為舊版本。
- AI 顧問只能追問已保存的策略；資料改變後必須先產生新版策略。
- 同一案件不同階段的 RRI 結果不得互相覆蓋。

至少驗收這 5 種情況：

1. 只有刊登資料。
2. 看房後補充漏水或設備狀態。
3. 房東回覆與刊登內容矛盾。
4. 談判後條件改變。
5. 契約文字與先前承諾不一致。

通過標準：

- 每個結果都能回答「根據哪個時間點的資料」。
- 更新資料後不會默默沿用舊策略。
- 使用者能保留舊版本並產生新版，而不是覆蓋歷史。

### 關卡 5：保護契約原文與人工決定（P0）

目的：AI 可以犯錯，但不能讓錯誤結果取代原始契約。

要完成：

- 原始檔案、擷取文字、AI 候選欄位、人工修正分開保存。
- 同一檔案以 SHA-256 辨識，避免重複上傳造成混淆。
- 只有人工接受或修改過的候選內容可以進入 RHIR。
- 拒絕的候選內容不得偷偷回到分析結果。
- 報告顯示判斷時，要能找到對應原文與前後文。
- 免費擷取不足時，使用付費 OCR 前仍需取得明確同意。

通過標準：

- AI 重新擷取不會覆蓋原檔。
- 人工修正後重新載入，內容仍一致。
- 被拒絕內容不會影響 RRI、AI 分析與策略。
- 相同檔案可以辨識為重複來源。
- 原始文件只有該瀏覽器擁有者可以讀取。

### 關卡 6：收緊 RHIR 欄位與案例對應（P1）

目的：避免不同拼法或臨時欄位讓案例查詢悄悄變成空結果。

要完成：

- 核心 RHIR 細項欄位必須有正式清單。
- 新欄位不得只出現在案例中，卻沒有名稱、用途與限制說明。
- `partial`、`inferred`、`supplemented` 等狀態要明確決定是否支援。
- 找不到精確案例時，要明確顯示「目前沒有精確案例」，不能假裝有依據。
- 案例仍只允許 `verified` 狀態進入高可信度建議。

通過標準：

- 字典檢查沒有未知核心欄位。
- 每種允許狀態都有明確結果或明確空結果。
- AI 不會引用未審核、已退回或已排除案例。

### 關卡 7：資料保存與恢復（P1）

目的：避免重新整理、換案件或清除瀏覽器資料後，使用者誤以為資料仍安全保存。

要完成：

- 清楚區分只存在本機的草稿與已存入線上資料庫的正式紀錄。
- 儲存失敗時不能顯示成功。
- 同一案件、不同版本的內容不能互相載入。
- 清除瀏覽器資料後無法取回匿名資料的限制，要在介面與文件說清楚。
- 正式登入導入前，不宣稱支援跨裝置同步。

通過標準：

- 重新載入後可取回同案件、同版本資料。
- 切換案件時不會看到上一間房的資料。
- 斷線儲存時有明確失敗提示。
- 本機草稿與線上正式紀錄的名稱不會讓人混淆。

### 關卡 8：風險結果的一致性（P1）

目的：同一份資料每次都產生相同的基本風險結果，AI 只負責解釋，不改寫客觀分數。

要完成：

- 相同 RHIR 輸入必須得到相同 RRI 分數與區間。
- 缺漏、矛盾與已揭露資訊要維持不同處理方式。
- 個人偏好只能影響策略排序，不能改寫客觀風險。
- AI 分析若無可用案例，要誠實顯示缺少依據。
- AI 回傳不存在的案例識別碼時，程式必須移除該引用。

通過標準：

- 固定測試資料重跑後結果一致。
- 不同生命週期階段只因資料改變而改分，不因畫面切換而改分。
- 關閉 AI 後，RRI 與基本白話報告仍可產生。

### 關卡 9：發布前收尾（P2）

目的：確保穩定版本可被團隊重複確認與回復。

要完成：

- README 的啟動、資料庫設定與檢查指令保持最新。
- 有一個清楚的穩定版本標記。
- 每項已知限制都寫明影響範圍。
- 未追蹤素材與舊分支完成處置決定。
- 新功能只能從已通過 P0、P1 的版本分支出去。

通過標準：

- 新成員只看 README 與本清單，就能執行靜態檢查。
- 發布問題發生時，可以回到上一個穩定版本。
- GitHub 與本機穩定版本一致。

## 五、執行順序

不得跳關；每關完成後再決定下一關的實作方式。

1. **A：Git 與素材邊界**——完成關卡 0。
2. **B：資料保護**——完成關卡 1、3。
3. **C：可判讀的檢查流程**——完成關卡 2。
4. **D：核心資料一致性**——完成關卡 4、5。
5. **E：結果可信度**——完成關卡 6、7、8。
6. **F：穩定版本封存**——完成關卡 9。

建議第一個實作項目是關卡 1。原因不是它最華麗，而是目前匿名訪客可修改案例審核資料；在這個問題解決前，新增更多依賴案例的功能只會放大風險。

## 六、本機靜態檢查指令

以下指令都在專案根目錄執行，不需要進行瀏覽器驗收。

```powershell
npm run evidence:dictionary:validate
npm run evidence:insight-context:test
npm run strategy:ui:test
npm run strategy:session:test
npm run lifecycle:test
npm run rri:stage:test
npm run documents:test
```

期待結果：7 項全部結束且沒有錯誤。

### 線上資料檢查

```powershell
npm run evidence:mappings:validate
npm run evidence:retrieval:test
```

期待結果：2 項全部通過。若出現 `fetch failed`，先檢查 Supabase 專案是否存在、網址能否連線，再判斷是否為程式錯誤。

### Git 邊界檢查

```powershell
git status --short --branch
git rev-list --left-right --count HEAD...origin/main
```

期待結果：位於預期分支，且本機與 GitHub 的差異為 `0 0`。未追蹤素材仍可存在，但不得被意外放入本次提交。

## 七、新功能解鎖條件

只有同時滿足以下條件，才建議開始新功能：

- 關卡 0 至 5 全部通過。
- 關卡 6 至 8 沒有會造成錯誤結論或資料遺失的問題。
- 9 項靜態檢查全部通過；若線上服務暫時中斷，必須留下原因與重新驗證方式，不能把失敗標成通過。
- 案例修改權限不再對匿名訪客開放。
- 契約原文、人工修正與歷史策略都有保存邊界。
- 本機與 GitHub 已同步，且有可回復的穩定提交。

每次只回報可驗證的結果：

```text

仍未確認的部分：

```

若某項沒有驗證，就明確寫「未驗證」，不能用「應該正常」代替。
